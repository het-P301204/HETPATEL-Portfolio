Why an allow-list kept failing open

Status
closed
Origin
self-initiated
Started
2026-02-19
Published
2026-03-04

A test environment I had built for something else kept accepting requests that its allow-list should have rejected. The rule read correctly. I wanted to know where the gap between the declared rule and the observed behaviour was coming from, because a rule that is right on paper and wrong in practice is a more interesting failure than a rule that is simply wrong.

My first instinct was to read the configuration, and I deliberately did not. Reading the rule first tends to make you see what you expect to see — you confirm that the pattern is correct, conclude the problem is elsewhere, and lose an hour. So I started from the other end: I captured what actually reached the service and worked backwards toward the rule.

That meant logging the request as the application received it, not as the client sent it. The two differed. By the time a request arrived at the handler, its path had been rewritten — a trailing segment normalised, a duplicated separator collapsed. Small changes, none of them wrong on their own.

Once I could see both forms side by side, I compared them against the rule directly rather than through the application. The matcher was being handed the pre-normalisation path.

I had assumed normalisation ran first because that is the order I would have written it in. Worth remembering that the order I would choose is not evidence of the order that exists.

The rule was correct. The ordering was not. Normalisation ran after the match, so a request could match nothing, be rewritten into a form that would have matched, and then be handled anyway. The allow-list was being consulted about a string that no longer existed by the time the request was served.

This also explained why it looked intermittent. Requests whose paths survived normalisation unchanged behaved exactly as expected, which is most ordinary traffic. Only the requests that were rewritten fell through, and those were the ones nobody was sending deliberately.

What I could not determine was whether the ordering was deliberate. There is a plausible performance argument for normalising once, late, rather than on every candidate comparison — and if that was the reasoning, the failure is a consequence of a defensible decision rather than an oversight. Establishing which it was would need the change history, and this was a environment I had assembled myself from defaults, so there was no history to read. I have left it open rather than guessing, because "someone made a reasonable trade-off and did not notice the consequence" and "someone got the order wrong" call for different fixes.

Revisions

2026-05-21
The original conclusion described this as an access-control failure. Re-reading the request sequence, the matcher is never reached for rewritten paths at all — so it is a routing failure that happens to have an access-control consequence. Changed the conclusion.
2026-07-09
Removed a claim that this pattern was common. I had seen it twice and generalised from that, which is not enough to support the word.
